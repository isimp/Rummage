# Technical notes

How Rummage works, which other mods it relies on and how, and how it is built and tested. Rummage runs only in the game client (`BepInProcess("valheim.exe")`); a dedicated server never loads it.

## Dependencies

| Mod | How Rummage needs it |
|---|---|
| AzuCraftyBoxes 1.8.27 or later | Required. A hard `BepInDependency` with that minimum version and the package manifest's dependency, so BepInEx does not load Rummage without it and mod managers install it alongside. It decides which chests Rummage may use and what may leave them. |
| MultiUserChest | Optional. With it, chests another player's game holds can be used; without it, they are left alone. MultiUserChest itself must be on the server and every client. |
| ExtraSlots | Optional. With it, its equipment, quick, food and ammo slots are never filled, except the stack a top-up fills. |
| AzuAntiArthriticCrafting | Optional. With it, a recipe is taken for the craft amount set in its crafting tab. |

Every one of them is reached by type and member name at startup, never as a build reference, so Rummage builds without them. A member that cannot be found is logged once and its part is switched off. The startup line in the log says what was found.

## Layout

`src/Core` decides everything that needs no game: the plan of a grab (`Planner`), what the chests can give (`Stock`), how many a press is for (`Repeat`), costs (`Cost`), the search (`Search`, with `Query` reading the text), every line the player reads (`Report`, `Readout`, `Locate`), the wait for other players' answers (`Waiting`), the search box's list and rules (`ListWindow`, `SearchBoxRules`), what it lists and when its pieces and recipes are made again (`CatalogRules`), what the grab key is for (`ContextRules`), what a recipe costs and makes (`RecipeRules`), who may use a chest and how (`ChestRules`), how a grab is named (`Labels`), which chests stay lit (`Lights`), which pings are up on the map (`Pings`), where the lines show (`Placement`) and the file per character of what the search box last used (`RecentFile`). It has no Unity or BepInEx reference, so `tests/Rummage.Tests` builds it on its own. `src/Game` reads the game and the other mods into the core's terms, carries out the result and draws what the player sees. `src/Plugin.cs` reads the keys and `src/Settings.cs` holds the settings. `selftest/` is the in-game self-test, a plugin of its own.

## The key

With the inventory open, the key is for a stack of the player's under the cursor (found as the inventory grid finds it, `InventoryGrid.GetHoveredElement` and `GetElementPos`), else the recipe selected in the crafting tab (`InventoryGui.m_selectedRecipe`). Otherwise it is for the build piece under the cursor in the build menu (`Hud.m_hoveredPiece`), else the piece being placed (`Player.GetSelectedPiece`), which is the piece the game's build panel shows. Each of these can be turned off (`TopUpStacks`, `TakeForRecipes`, `TakeForPieces`), and is then passed over. With none of them, the key opens the search box, unless `KeyAloneOpensSearch` is off; with the search modifier (`SearchModifier`, Shift by default) or a search key of its own (`SearchKey`), it opens the search box on the recipe or piece, its count filled in. All of this is `Plugin.Press`, which the self-test presses too.

A piece or recipe is a total to carry: what the inventory already holds counts, and only items at or above the world level count, as building and crafting only take those. A recipe follows the crafting tab's rules: a new item at quality 1, an upgrade at the next level, each requirement at `Requirement.GetAmount(quality)`, an upgrade station's own parts only at such a station. A new item is taken for AzuAntiArthriticCrafting's craft amount (`HaveRequirementItemsTranspiler.GetCurrentCraftAmount`), or for one craft without it. For a recipe that needs only one ingredient (`m_requireOnlyOneIngredient`), only ingredients the player knows are offered, as in the game; each is planned on its own, and the one carried in full already is chosen, else the first the chests make up in full, else the closest (`Choice.Best`).

Each press is for one more than what is carried already pays for (`Repeat.Next`): a piece counts what the inventory pays for in whole pieces and asks for one more, and a recipe steps by the craft amount. Only parts the chests can still give decide what is paid for, so a part they have run out of does not hold the count down; when no part can come from the chests, all parts decide and the count stays.

`PiecePress` changes this for pieces only (`Core/Presses.cs`). `TopUp`, the default, is the rule above. With `FullSet` a press for a piece is for one, and what the inventory holds does not count (`Want.CountCarried` off), so every press brings the piece's whole cost and presses for different pieces add up. A count typed in the search box for a piece follows the same rule, and the search box counts a piece by the whole sets the chests alone can give. Recipes count what is carried under either rule, and items are always a number to bring.

A stack under the cursor is filled to a full one, or by at most `TopUpAmount` when that is above zero (`Want.TopUp`): only items that stack with it (same item and world level, and quality for items with quality levels), and only into its own slot, whatever kind of slot that is.

## Where from

The chests are AzuCraftyBoxes' list (`API.GetNearbyContainers` at its own `Container Range`). That list already leaves out chests the player may not open, warded chests, chests open in another game, carts in use and chests its own toggles exclude; mods that seal chests from automation keep them out of it. Entries that are not vanilla chests (item drawers, the player's bags) are skipped. AzuCraftyBoxes checks access only when it first lists a chest and never takes a chest off its list, so before Rummage takes from, finds in or counts a chest, it asks again what the game asks when a chest is opened by hand (`Game/Access.cs`): the game's ward check, and so the rules of any mod that changes it, and the chest's privacy. A chest the player could not open now is only read, to say why something is missing. A chest's rules come from `API.CanItemBePulled` with the chest's and the item's prefab names. `Leave One Item` and `Container Range` are read from AzuCraftyBoxes' own config entries, so a server's synced values apply.

## The plan

`Core/Planner.cs` takes the nearest chest first. With `Leave One Item` on, each chest keeps one unit of each item it holds, counted by item rather than by stack, as AzuCraftyBoxes counts it (`Stock.Budget`, which the search list's counts use too). Each take is sized to land whole in one inventory slot: a part stack of exactly the same kind first, then an empty slot ordinary items may use. Takes from chests this game holds happen at once, so several may fill one slot; a take from another player's chest is answered later and its slot stays reserved until then (MultiUserChest's `InventoryBlock`), so that slot gets nothing more in the same grab, and a top-up waiting that way says to press again for the rest.

## The takes

Each take is `Inventory.MoveItemToThis(chest, item, amount, x, y)`, the call the inventory screen makes for a drag. It adds to the inventory and lowers the chest's stack in the same step, so an item is never in both places.

The game saves a chest only in the game that holds it (its ZDO owner); a change made anywhere else would be lost the next time the chest reloads, while the items would already be in the player's inventory. So:

| The chest is held by | Rummage |
|---|---|
| This game | Takes directly. |
| Another game, MultiUserChest loaded | Hands the take to MultiUserChest, which asks that game; that game removes the items and sends them back. |
| Another game, no MultiUserChest | Leaves the chest alone. |
| No game, or MultiUserChest ignores it | Leaves the chest alone. |

MultiUserChest takes over the same call through its `Inventory.AddItem` prefix, but only for an item it knows to be in that chest. Before each take Rummage checks that it does (`InventoryPatch.InventoryOfItem`), and after it that the chest is unchanged here and the target slot is held for the answer (`InventoryBlock.IsSlotBlocked`); a take that fails either check is not counted. The next grab waits until every slot of the last one is released, or 10 seconds. If the chest changed meanwhile, the holding game hands over what is now in that slot; if the player leaves before the answer, the answer is lost. Both are how MultiUserChest works for a drag too.

## What the player reads

After a press (`Core/Report.cs`): for a piece or recipe, each part as now carried over needed, with what the press added and what is on its way from another player's chest; for an item, what was taken and what was asked of other players' chests. Each shortfall gets a reason: kept back by `Leave One Item`, kept in by chest rules, in a chest someone has open, in someone's private chest (named without its count), in a chest the player may not take from, in a chest another game holds, no room, or not in chests nearby. For these reasons the chests in reach that AzuCraftyBoxes does not list are read too (`Scene.AddBarred`: its own registry, then one physics query over the building-piece and cart layers into a reused buffer), never to take from. What is short, except for want of room (`Locate.SoughtFurther`), is then looked for in the chests past AzuCraftyBoxes' range and within the find radius that a find would look in (`Finder.FindFar`, lines from `Locate.TooFar`): a line per item any of them holds, after the shortfalls, says how many, in how many chests, how far the nearest is and that it is too far to take, and those chests are lit and pinged as a find lights them. Without AzuCraftyBoxes' registry there is nothing past its range to look in. Once every answer from other players' chests is in, `Report.Arrivals` says per item what arrived, what was turned down and what had no answer. How much is told follows `Messages`: everything (the default), what was taken and what is short without the reasons, or nothing after a grab or an answer; what finding turns up is always told, and the lines on chests too far to take from follow `Messages` like the rest of a grab's, under `Short` too, while their chests are lit and pinged whatever it says. Lines go to the corner as the game's own messages, or, while the inventory is open and covers the corner, as one message in the middle of the screen (`Game/Notice.cs`). Chests taken from light up for `TakeGlow` seconds (2 by default; 0 lights none) and get no ping.

While building, a small table in a box to the right of the game's build panel, as tall as the panel and at most 520 units wide (`Game/BuildReadout.cs`, text from `Readout.Panel`), shows a row per part: what the inventory holds against the next press, orange where the press would make it up and red where it cannot, and how many the press would take, with what would still be short. Its columns are placed with TextMeshPro's `pos` tag after the widest entry before them, measured in the text's own font. Under `PiecePress` `FullSet` the table is headed *One more* and shows what the inventory holds as a plain number beside the whole set the press takes (`Readout.FullSetPanel`). `BuildBox` set to `UntilCarried` hides it while the inventory holds enough to build one of the piece, under either rule, and it never shows while `TakeForPieces` is off. The text is a duplicate of the panel's own description text object in a dark box, so it has the game's font. It is looked at twice a second and right after a press, and worked out again only when a fingerprint of what it depends on changes: the piece, every inventory stack, each chest in reach with its data revision and holder, and the settings.

## The search box

`Game/Palette.cs`, drawn with Unity's immediate-mode GUI in the game's own art (`Game/UiArt.cs`): sprites from the game's `UIAtlas` (`woodpanel_settings`, `text_field`, `button`, `button_highlight`, `button_small`) drawn as nine-part frames, a dark inner panel so text stands out on the wood, item, piece and recipe icons and the game's orange and beige. Where a sprite cannot be had, plain fills stand in. It is sized to the screen's height times `Scale` and shows `Rows` results at once. It draws through a component switched on only while it is open, and once early in a world to warm the fonts (the first text drawn in a session otherwise costs the better part of a second).

When it opens it reads the chests once (`Game/Catalog.cs`), listing what `ShowItems`, `ShowPieces` and `ShowRecipes` leave on: every item the chests within the find radius hold, with how many of those a grab could take, so an item that cannot be taken is still listed and can be found; every piece the build menus would show (enabled and in the player's known recipes); and every known recipe at quality 1. Pieces and recipes with their costs and icons are kept between openings and made again only when the known recipes or materials, the player, the world's item list or the language change.

`Core/Search.cs` reads the text against the names it may stand for (`Query.Parse`): when its words are the first words of a name, numbers included, it is that name; otherwise a whole number at either end is the count. It ranks the whole name first, then names starting with the text, then a word starting with it, then the text inside a word, then its letters in order; among equal matches the shorter name comes first, then what the chests hold most of. With nothing typed, it lists the new items row, then what was last found or taken, then everything the chests hold by name. Tab (`Query.Complete`) puts the chosen name in, the count in front.

Enter without a count finds (`Game/Finder.cs`, lines from `Core/Locate.cs`): every chest AzuCraftyBoxes has registered within the find radius (`FindRadius`, 50 m by default; the ones the player may use and ones someone else has open; other players' private chests are never registered) is counted for the item, or for each part of a piece or recipe, and the chests holding any are lit for `FindGlow` seconds (6 by default) with the game's own highlight, given again every tenth of a second as it fades after a fifth (`Game/Highlighter.cs`). Enter with a count takes it; *Take* takes the slider's count.

Each chest a find lights also gets a ping on the map (`Game/Pinger.cs`, timing in `Core/Pings.cs`): a pin of the game's `Ping` type added with `Minimap.AddPin` with saving off, at double size and pulsing like a ping a player sends, named by what the chest holds of each item looked for (`Locate.PinName`, shown on the large map only, as the game shows names only there). It is never sent: the game's own ping goes to every player through the `ChatMessage` routed call and keeps one per player, so it could not mark several chests. A chest pinged again gets its new pin in place of the old one, each pin is removed after `PingSeconds` (0 puts none up), and while any is up the map is told every frame to redraw its pins (`m_pinUpdateRequired`), which it otherwise does only on a change and which the pulse needs. When the map is a new one, the pins went with the old. A chest outside the small map's view is not drawn there, as the game draws no pin at the edge.

The search box remembers the last two things it found or took (`Core/Recent.cs`), by kind and key, so an item and a recipe of the same name stay apart. The most recent find stays found until it is taken or something else is found; Enter without a count on it then takes one (`EnterDoes.TakeOne`): one item, or for a piece or recipe what a press of the key would take. Shift with Enter always finds. These rows come first with nothing typed, carry the game's `refresh_icon` sprite before the name and say *found* or *taken* in front of their text; an item no chest nearby holds any more stays listed as *none nearby*. A recipe is remembered only at quality 1, as the search box lists it, so an upgrade is not. `Game/LastUsed.cs` keeps them for each character in `BepInEx/cache/isimp.Rummage/last-used/<player id>.txt`, one line each, written beside the file first and then copied over it. The cache folder is used because a mod manager's profile sync replaces the config folder. A file that cannot be read or written is told once in the log and the search box goes on with what it holds. `/rummage forget` clears them in memory and deletes the file. With `RememberLastUsed` off the search box sees nothing remembered, remembers nothing new and Enter without a count always finds; the file is left as it was, so turning it back on brings back what was remembered before.

While it is open, `TextInput.IsVisible` answers yes, which stops the player's movement, actions, chat and menu and frees the cursor; the inventory's update waits, as it reads Tab, Escape and the use key without that check; and the mouse wheel reads nothing outside the box. All three hold for two frames after it closes, and the game's chat and inventory keys are cleared then, so the Enter or Escape that closed it opens nothing. Each of these patches stands aside for the session if it ever fails.

## New items

`Core/NewItems.cs` lists one of every item in the chests in reach that is not in the player's `m_knownMaterial`, nearest chest first. Chests the player may not use are not looked into, so a private chest gives nothing away, and any world level counts, as carrying any copy teaches the item: the game adds every item in the inventory to that list when the inventory changes (`Player.OnInventoryChanged` → `AddKnownItem`), which updates the known recipes and pieces. The grab is an ordinary one with a count of one per item, so `Leave One Item`, chest rules, other players' chests and the report work as for any other. The search box shows a *New items* row first when the chests hold anything new; Enter on it reads the chests again and takes. `/rummage new` (`Game/Commands.cs`) does the same. The game keeps one handler per chat command, so `/rummage` dispatches its words there and the self-test adds `selftest` to it.

## Self-test

`selftest/` is a plugin of its own, `Rummage.SelfTest`, reaching into Rummage through `InternalsVisibleTo`. It is built and deployed with a development build and built in CI so it keeps up, and it is never packaged: a release takes `Rummage.dll` alone. `/rummage selftest` in chat runs it where the player stands, and the results are `[selftest]` lines in `LogOutput.log` ending with a `DONE` summary.

It runs on the settings as they ship, without writing them to the config file, and puts the player's own back at the end. It sets the player's belongings (all but what is equipped) aside in vault chests it builds, builds test chests in front of the player (two to take from, a private one, and someone else's private one) and narrows Rummage's chests to them while it runs (`CraftyLink.OnlyChests`). Each part starts from refilled chests and an emptied inventory and goes through the key's own entry points (`Context.Find`, `Grabber.Grab`, the search box's text, Tab and Enter). After every grab it checks that the inventory and the test chests together hold exactly what they held before. Its parts cover a piece selected with the hammer pressed twice, counting past a missing part, the build panel lines, `Leave One Item`, chest rules, chests that may not be used, a listed chest put under a ward owned by nobody (skipped when the game lets the player into every ward, as an admin bypass does), a full inventory with one part stack, a recipe pressed twice, filling a stack, the search box (find with its glow and its pings on the map, take, Tab, names ending in a number), a chest built past AzuCraftyBoxes' range and within the find radius (skipped when AzuCraftyBoxes has no registry, when the find radius reaches hardly past that range, or when the chest is not listed there: a short grab names it after the shortfall, takes nothing from it, lights and pings it alone; a grab short of nothing looks no further; `Messages` `Short` and `Off`; `FindGlow`, `TakeGlow` and `PingSeconds` at one second, gone a second later, and at 0), a piece under `PiecePress` `FullSet` (each press a whole set on top of what is carried, the build box, `UntilCarried`, two whole sets typed in the search box), what the search box last found or took (listed first and marked, Enter on what it found takes one, taking it or finding something else ends the find, Shift with Enter, read back from the character's file, `/rummage forget`, `RememberLastUsed` off; the player's own are set aside while the test runs and put back after), new items (stone and wood arrows taken off the list of what the character has carried and put back on it after; `/rummage new`, the search box row, `Leave One Item`), the settings (what the search box lists, the key with nothing in front, the targets turned off, `BuildBox`, `TopUpAmount`, `Messages`), a chest handed to an owner that does not exist (MultiUserChest's request is never answered: the chest must not change here and the wait must end), a chest handed to a nearby player's game the way opening a chest hands it over (skipped when nobody else is within 30 m), and how long each step takes on the chests really in reach. Everything is put back at the end; what cannot be put back stays in its vault chest, left standing and reported with its place.

## Building

```
dotnet build                     # against the installed game, deploys to the Gale profile
dotnet build selftest            # Rummage and the self-test
dotnet build -p:LibsDir=lib      # against the stubs in lib/, as CI does
dotnet test tests/Rummage.Tests
dotnet test tests/Rummage.Standards
```

`VALHEIM_DIR` or `-p:ValheimDir=` points at the game, `-p:ProfileDir=` at the BepInEx profile.

The build itself runs every .NET code analysis rule and fails on any finding (`BuildChecks.props`), but for the few that misread a Unity plugin, which `Analysis.globalconfig` turns off with the reason for each. It also compiles the doc comments, so a link to something renamed fails it. `tests/Rummage.Standards` holds what the compiler cannot. It compiles Rummage's source as the build does, against the stubs in `lib/`, and reads it with the compiler's own types. Text is compared and sorted ordinally, never in the PC's language, and a fraction or a time becomes text the same way on every PC. A Unity object is checked for none by Unity's own test. A failure caught is told in the log, or the catch says what the failure means. Comments carry no dates, each member has one summary of its own, every file under `src/` is compiled into the unit tests or named in `GameOnlyFiles.cs` with why it needs the game, every test-only `Reset()` forgets all its class holds, and the plugin, the project and `manifest.json` name one version. Neither set needs a `BepInEx.dll`, so the build workflow runs both on every push.

`.githooks/pre-push` runs both sets before every push and stops the push when one fails, and `.githooks/commit-msg` refuses a message that carries a clock time. The pre-push hook also runs `tools/check-shared.sh`, which compares the files listed in `tools/shared-files.txt` with Bindrune's copies beside this repository (the same but for the mod's name) and stops the push where one changed without the other; without a Bindrune checkout it says so and compares nothing. Git uses them once told to, per clone: `git config core.hooksPath .githooks`.
